你将为一个tmod项目创建或维护一组结构相似、风格一致的项目文档流。请严格遵循以下约束，并在动笔前先检查现有仓库状态与已有 docs 内容，避免凭空改写历史。

项目文档流目标：
建立一套从"文档入口 -> 稳定架构 -> 路线图 -> 自动化测试报告 -> 手工验证报告 -> 实现总结 -> 临时阶段任务流程"的连续文档流。文档应能服务长期维护、跨会话交接、跨环境验证，以及后续快速定位架构决策、待办、验证证据和历史实现状态。

总体文档位置：
- 稳定项目文档统一平铺在 `docs/` 下。
- 临时跨会话阶段任务统一放在 `docs/work-items/` 下。
- 根目录只保留 `README.md`、`LICENSE` 等少量根级文件，不把普通项目文档散落到根目录。

命名规则：
- 稳定文档使用 `NN-category-topic.md`。
- `NN` 必须是两位数字，用来控制阅读顺序。
- `category` 使用小写英文类型，例如 `guide`、`design`、`plan`、`report`、`process`、`workitem`。
- `topic` 使用小写 kebab-case，简短、具体、可读。
- 推荐序号范围：
  - `00-09`：文档指南、目录、索引。
  - `10-19`：设计、架构、模块边界。
  - `20-29`：路线图、计划、待办。
  - `30-39`：测试、验证、实现摘要等报告。
  - `40-49`：流程、工作规则。
  - `50-79`：必要时提升到主 docs 集合的阶段任务。
  - `80-99`：必须留仓库的归档或迁移说明。
- 临时阶段任务文件使用 `docs/work-items/YYYY-MM-DD-short-topic.md`。

必须创建或维护的核心文档流：

1. `docs/00-guide-documentation.md`
   职责：
   - 作为文档目录与维护规范入口。
   - 列出所有稳定文档及其用途。
   - 定义命名规则、序号范围、职责边界和 work-item 规则。
   - 明确完成阶段任务后的归档/合并流程。
   不应包含：
   - 具体实现细节。
   - 临时验证日志。
   - 已完成历史的大段总结。

2. `docs/10-design-architecture.md`
   职责：
   - 记录当前稳定架构，而不是旧迁移草案。
   - 描述模块结构、分层职责、平台/环境职责、核心运行流程、部署模式、持久化生命周期、关键处理流程、当前约束和维护规则。
   - 聚焦长期有效的设计决策、边界、数据身份和运行语义。
   应包含的典型章节：
   - Design Goals / 设计目标
   - Module Structure / 模块结构
   - Layer Responsibilities / 分层职责
   - Platform Responsibilities / 平台职责
   - Key Runtime Flows / 核心运行流程，可按领域拆分，例如 Deployment Modes、Persistence Lifecycle、Core Processing
   - Current Constraints / 当前约束
   - Maintenance Rules / 维护约定
   不应包含：
   - 构建命令结果。
   - 覆盖率数字。
   - 每轮修复流水账。
   - 未确认的临时想法。

3. `docs/20-plan-roadmap.md`
   职责：
   - 记录当前活跃待办、优先级路线图、已知限制和临时需求缓冲区。
   - 使用 P0/P1/P2/P3 等优先级表达风险与紧急度。
   - P0 通常表示验证与正确性，P1 表示测试覆盖或核心语义，P2 表示用户可见功能，P3 表示清理维护。
   应包含的典型章节：
   - Checklist Summary / 勾选简表
   - Priority Roadmap / 优先级路线图
   - Long-Term Maintenance / 长期维护
   - Known Limitations / 已知限制
   - Request Buffer / 临时需求缓冲区
   不应包含：
   - 已完成实现历史。完成项应移入 `32-report-implementation-summary.md`。
   - 自动化测试证据。证据应移入 `30-report-tests.md`。
   - 手工实机验证证据。证据应移入 `31-report-verification.md`。

4. `docs/30-report-tests.md`
   职责：
   - 记录自动化测试范围、覆盖快照、构建验证和编译证据。
   - 用于当前交付的自动化证据，不替代运行时验证报告。
   应包含的典型章节：
   - Purpose / 用途
   - Automated Tests / 自动化测试
   - Coverage / 覆盖率
   - Build Verification / 构建验证
   - Automated Persistence Coverage / 自动化持久化覆盖，如适用
   - Runtime Validation Boundary / 运行时验证边界
   - Notes / 说明
   写法约束：
   - 命令必须用反引号包裹，例如 `mvn test` 或 `pytest tests/`。
   - 结果必须明确写 passed/failed 或中文"通过/失败"。
   - 覆盖率快照要写清指标名称、covered/total 和百分比。
   - 可以提及运行时验证缺口，但只用于解释为什么自动化测试无法覆盖，具体手工结果归 `31-report-verification.md`。

5. `docs/31-report-verification.md`
   职责：
   - 面向交付记录修复验证、集成预期、已完成手工验证和仍需手工验证。
   - 区分"已修复问题""预期行为""已完成手工验证""剩余手工检查"。
   应包含的典型章节：
   - Purpose / 用途
   - Fixed Issues / 已修复问题
   - Integration Validation Summary / 集成验证摘要
   - Manual Validation Completed / 已完成手工验证
   - Remaining Manual Checks / 仍需手工验证
   - Notes / 说明
   写法约束：
   - 修复项适合用编号列表，英文一条、中文一条，连续编号可以中英交替。
   - 预期行为要按部署模式、交互路径、兼容对象或风险领域分组。
   - 未完成验证必须明确保留为 checklist/条目，不要伪装成已验证。

6. `docs/32-report-implementation-summary.md`
   职责：
   - 记录已完成实现范围和历史项目状态。
   - 它不是活跃 backlog。
   应包含的典型章节：
   - Purpose / 用途
   - Completed / 已完成
   写法约束：
   - 只写已经完成、已经合入或当前仓库实际存在的能力。
   - 不写未来计划；未来计划放 `20-plan-roadmap.md`。
   - 不写详细测试证据；测试证据放 `30-report-tests.md`。

7. `docs/40-process-work-items.md`
   职责：
   - 定义何时创建临时阶段任务、命名规则和模板。
   - 说明 work-item 完成后的收束流程。
   应包含的典型内容：
   - Create a new file when / 需要新建文件的情况
   - Use this name format / 使用以下命名格式
   - Suggested template / 建议模板
   Work-item 模板：
   ```markdown
   # Short Topic

   Last updated: YYYY-MM-DD

   ## Goal

   ## Scope

   ## Checklist

   - [ ] ...

   ## Decisions

   ## Validation

   ## Handoff Notes
   ```

双语风格约束：
- 文档标题通常先英文，下一行中文，例如：
  - `# Test Report`
  - `# 测试报告`
- 日期字段成对出现，例如：
  - `Last updated: YYYY-MM-DD`
  - `最后更新：YYYY-MM-DD`
  或：
  - `Date: YYYY-MM-DD`
  - `日期：YYYY-MM-DD`
- 章节标题通常英文一行、中文一行，例如：
  - `## Purpose`
  - `## 用途`
- 条目通常英文一条、中文一条紧邻出现，保持语义对应。
- 中文使用简体中文。
- 技术名词、类名、方法名、命令、路径、配置项使用反引号，例如 `UserService`、`getUserById`、`application.yml`。
- 不要为了翻译而翻译代码标识符；代码标识符保持原样。
- 语气应是工程文档风格：准确、克制、可维护，不写营销话术。

内容边界硬约束：
- 架构长期决策只进 `10-design-architecture.md`。
- 活跃待办、优先级和已知限制只进 `20-plan-roadmap.md`。
- 自动化测试、覆盖率、编译/构建证据只进 `30-report-tests.md`。
- 手工运行验证、集成预期和剩余人工检查只进 `31-report-verification.md`。
- 已完成实现范围和历史状态只进 `32-report-implementation-summary.md`。
- 跨会话但临时的执行计划只进 `docs/work-items/`。
- 完成 work-item 后：
  - 长期有效决策合并进 `10-design-architecture.md`。
  - 剩余待办合并进 `20-plan-roadmap.md`。
  - 自动化验证摘要合并进 `30-report-tests.md`。
  - 手工验证摘要合并进 `31-report-verification.md`。
  - 已完成实现范围合并进 `32-report-implementation-summary.md`。
  - 原 work-item 若无追溯价值可删除；若有历史价值，整理后归档。

生成或更新文档时的工作流程：
1. 先读取现有 `docs/` 目录和相关源码/构建文件，确认项目真实状态。
2. 判断本次信息属于哪一种文档职责，不要把同一内容重复塞进多个文档。
3. 保持现有双语结构、标题层级和列表风格。
4. 更新日期字段为实际更新日期。
5. 新增条目要落在正确章节中，必要时补充英文和中文对应条目。
6. 如果新增功能影响架构、路线图、测试、验证和实现总结多个层面，只把各自摘要写入对应文档，避免复制整段相同内容。
7. 修改后检查：
   - 文件名是否符合编号和 kebab-case。
   - 文档是否仍平铺在 `docs/` 下，临时任务是否在 `docs/work-items/` 下。
   - 是否误把临时内容写入稳定文档。
   - 是否误把测试证据写入架构文档。
   - 是否遗漏中文或英文对应内容。

创建新文档流时的建议初始文件集合：
```text
docs/
  00-guide-documentation.md
  10-design-architecture.md
  20-plan-roadmap.md
  30-report-tests.md
  31-report-verification.md
  32-report-implementation-summary.md
  40-process-work-items.md
  work-items/
```

最小可用初始内容要求：
- 每个稳定文档必须有英文标题、中文标题、日期字段、用途章节和至少一个主体章节。
- `00-guide-documentation.md` 必须列出所有稳定文档及职责边界。
- `10-design-architecture.md` 必须包含模块结构、分层职责、当前约束和维护规则。
- `20-plan-roadmap.md` 必须包含 checklist summary、priority roadmap、known limitations 和 request buffer。
- `30-report-tests.md` 即使暂无测试，也必须写明当前测试状态、缺口和预期命令位置。
- `31-report-verification.md` 即使暂无手工验证，也必须写明剩余手工检查。
- `32-report-implementation-summary.md` 只写已完成能力，不写"计划实现"。
- `40-process-work-items.md` 必须包含 work-item 创建条件、命名格式和模板。

禁止事项：
- 不要把 `docs/` 变成深层目录结构；除 `docs/work-items/` 外保持平铺。
- 不要在架构文档中写每次构建通过的流水账。
- 不要在路线图中长期保留已完成项目。
- 不要在实现总结中写未完成计划。
- 不要把运行时手工验证结果写进自动化测试报告作为测试覆盖。
- 不要创建只有中文或只有英文的稳定文档；保持中英双语对应。
- 不要夸大验证状态；未跑过就写"仍需验证"。
- 不要用易变身份描述持久化身份，除非该项目确实以此为设计。优先描述稳定逻辑身份和模块边界。

输出要求：
- 如果被要求"创建整套文档流"，请直接创建上述文件。
- 如果被要求"更新现有文档流"，请最小化修改，只更新职责对应的文档。
- 如果被要求"创建阶段任务"，请放入 `docs/work-items/YYYY-MM-DD-short-topic.md`，并使用 Goal、Scope、Checklist、Decisions、Validation、Handoff Notes 模板。
- 完成后简要说明创建/修改了哪些文件，以及哪些内容仍需人工确认或验证。
